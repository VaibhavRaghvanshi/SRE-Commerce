# Cart service design

Cart is the next owning service after the approved source price/stock backfill. Its root is `SRECommerce.Cart.API`, with its own solution and API/Application/Domain/Infrastructure/Tests projects. SQL Server database `SRECommerce_CartDB` owns carts, items, guest sessions, operation receipts and immutable checkout preparations.

Guest access uses an explicit random 256-bit capability, never a tenant header, cookie, email or guessable cart ID alone. Only its SHA-256 digest is stored. The browser creates the capability so a lost create response can be retried without storing a recoverable secret on the server. Guest writes validate the current public Tenant/cart capability and bind a narrow guest write scope. Authenticated calls use live Identity membership and selected tenant; the owning user ID is never accepted from a browser request. Guest and authenticated APIs are separate paths.

All item mutations use rowversions and a client operation ID. An immutable operation receipt binds the ID to its exact payload and cart, allowing safe retries after a timeout without adding quantities twice. Carts contain at most 50 distinct published variants, quantities have at most three decimal places, and line identities/metadata come from live Catalog HTTP contracts. Removing items marks them inactive; business/audit history is retained. Client prices, tax, discounts, user IDs and tenant IDs in request bodies are rejected.

Guest carts expire after seven days; customer carts after thirty days of activity. An expired or merged cart cannot be mutated. Merge requires both the authenticated customer's authority and possession of the guest capability, adds matching quantities once, preserves tenant isolation and closes the source guest session atomically. Variant visibility is checked again under the destination customer's current Catalog role, including B2B eligibility.

Cart GET returns saved item state independently of price/stock previews. A separate preview obtains a current authoritative Pricing quote and Inventory availability over HTTP. Checkout preparation requires the current cart version, live SKU visibility, a valid server quote and sufficient tracked availability, then persists a short-lived immutable preparation. It does not promise reserved stock or an order: Order owns atomic reservation, coupon capacity and saga compensation. Preparation snapshots contain no bearer tokens, guest secrets, cost prices or payment data.

Order-only internal APIs use narrowly scoped client credentials and validate the preparation's cart identity, customer/capability proof, expiry and source cart revision before any claim. Internal routes stay blocked at YARP. Live confidential-client provisioning remains under the earlier hold; isolated tests may provision clients inside uniquely named test Identity databases. No new shared business DbContext or cross-service SQL joins are permitted.

Angular will retain only tenant-scoped guest cart capabilities, use in-memory Identity access tokens, support add/update/remove/coupon summary, and merge after login through the normal PKCE callback. Cart presentation must show dependency failures honestly; a saved line is not evidence of current stock or a guaranteed selling price.
