# Storefront Configuration backend design

Own five projects and SQL database `SRECommerce_StorefrontDB` (port 5084). Storefront owns page structure/content/visibility; Theme owns visual tokens. No production assembly or database reference to Theme, Catalog or Tenant business persistence.

Typed, versioned documents contain header/footer options, navigation/menu links, banners, supported sections, product field visibility and per-device placement. Sections support hero, featured categories/products, new arrivals, best sellers, promotions, review visibility, plain text and business-specific product-field panels. References are IDs to Catalog, never copied price/stock authorization. Supported relative/HTTPS navigation/media URLs, plain text (no executable HTML), bounded arrays and unique section/menu IDs are validated before preview/save/publish. Device order/columns/visibility can differ. Bundled business templates give spices/fashion/grocery/general/custom appropriate fields. Custom page slugs are constrained and reserved application paths cannot be claimed.

Owned SQL tables: StorefrontPages (draft JSON + rowversion), LayoutVersions (immutable page snapshots), PublishedConfigurations (per-tenant/page assignment + monotonic sequence/rowversion), LayoutPublishHistory, LayoutTemplates (explicitly initialized platform catalog), own audit/inbox/outbox. Tenant-prefixed composite keys/FKs prevent foreign-tenant publication. SQL JSON constraints validate storage, domain rules validate the document. Publish/rollback use serializable transactions; audit/outbox commit together. No startup migration or physical deletion.

Manager/Owner writes, Staff reads; current PKCE user/selected tenant/live `storefront` module required. Public published page/fallback is presentation-only. SQL deadline, last valid in-process/optional Valkey snapshot, bundled business template and neutral default keep rendering available during dependency failures. Independent Theme availability cannot block obtaining a layout. API consumers later combine independently cached theme and layout and always ask live business APIs for prices, stock, authorization and payments.

Native SQL tests must cover publication/version/rollback, lost updates/concurrent first publication, tenant isolation/spoofing, unsupported content/unsafe URLs, different device order, module/session revocation, SQL/dependency outages and fallback, migration reapply/health/OpenAPI. Docker build is verifiable without credentials; runtime SQL/broker/cache account creation stays on owner-requested hold.
