# Identity service setup and verification

This service is separate from the existing .NET 8 API and Angular app. Do not change the legacy API's connection string or authentication wiring to cut over implicitly.

## Local SDK and build

```powershell
.\scripts\Install-IdentitySdk.ps1
.\scripts\Initialize-IdentitySecrets.ps1
Set-Location Backend
..\artifacts\dotnet10\dotnet.exe tool restore
..\artifacts\dotnet10\dotnet.exe build SRECommerce.Backend.slnx -c Release -m:1 -nr:false
..\artifacts\dotnet10\dotnet.exe test SRECommerce.Backend.slnx -c Release -m:1 -nr:false
```

The fixed SDK is 10.0.403, runtime/EF/Identity 10.0.14, OpenIddict 7.7.2. Official SDK SHA512 is verified; installation stays under ignored artifacts and does not modify global SDK selection. The Backend tool manifest pins EF tooling. On a machine with this stable SDK already installed, normal dotnet commands from Backend also work. Root .NET 8 global.json/solution are retained.

## Database migrations

Reviewed idempotent SQL is [identity-initial.sql](../database-migrations/identity-initial.sql). Use SQLCMD **-I** for QUOTED_IDENTIFIER, required by filtered indexes. The explicit service database was approved; do not run this script against the old SRECommerceDb.

```powershell
sqlcmd -S '.\MSSQL22' -E -C -b -I -d SRECommerce_IdentityDB -i docs\database-migrations\identity-initial.sql
```

The script is generated by the pinned EF tool after building, not with stale pre-migration assemblies. Migrations bound Identity login/token keys and OIDC GUID subjects, with data-length guards that refuse unsafe narrowing. They do not delete or reset existing source stores. Down methods are recovery source only; do not execute destructive rollback without approval.

The native development connection uses current Windows authentication and a locally trusted SQL certificate. Production startup rejects TrustServerCertificate=true. Local developer credentials may be sysadmin. The reviewed runtime-role script grants Identity-schema DML only. A separate restricted runtime login was provisioned for the approved local container; SQL checks confirmed no table-creation or legacy-database access. Its credentials are in ignored local configuration, never in this runbook or Git.

## Initialize and run

From the API directory, using the absolute local SDK path (or an installed stable .NET 10 host):

```powershell
$env:ASPNETCORE_ENVIRONMENT='Development'
<repository>\artifacts\dotnet10\dotnet.exe bin\Release\net10.0\SRECommerce.Identity.API.dll --initialize
<repository>\artifacts\dotnet10\dotnet.exe bin\Release\net10.0\SRECommerce.Identity.API.dll --import-legacy <reviewed-snapshot.json>
# --apply-import is a separate explicit write mode after reviewing the dry-run.
```

Initialization registers the known public PKCE client and platform role. It creates a development platform administrator only when explicit local Bootstrap credentials are present; no fixed password is bundled or printed. Existing credentials are not overwritten. Original legacy Admin never becomes platform SuperAdmin automatically.

From Backend:

```powershell
$env:Mailpit__Enabled='true'
..\artifacts\dotnet10\dotnet.exe run --project Services\Identity\SRECommerce.Identity.API --launch-profile identity-http
```

Service: localhost:5081; OpenAPI: /openapi/v1.json; live/ready health endpoints. Startup never automatically migrates/seeds. A separate local initialization command is required. Data-protection keys and development signing/encryption certificates remain outside Git. Back up and protect these separately from SQL backups; restoring a database alone does not restore decryption/signing keys.

## Local email

Docker engine must be available and memory sufficient before using the opt-in container:

```powershell
docker compose --profile identity-email config --quiet
docker compose --profile identity-email up -d mailpit
docker compose ps
docker compose logs --tail 50 mailpit
docker compose stop mailpit
```

The selected Mailpit readyz health command is verified against v1.32.0. Where Docker is unavailable, the same pinned Mailpit release can run as an officially downloaded SHA256-verified local binary; the implementation session used this fallback, bound only to 127.0.0.1 ports 1025/8025 and a dedicated ignored database. Do not send real external mail or enable SMTP relaying.

Email jobs commit with registration and encrypt their payload using the service's key ring. The local worker retries outages with bounded delay and stable Message-ID. This is a single local dispatcher with at-least-once delivery; multi-replica leasing/deduplication and real outbound delivery remain deployment work. No Notification microservice or broker was created implicitly.

## Real-process smoke test

Run the built API and dedicated Mailpit, then from the repository root:

```powershell
$env:IDENTITY_SMOKE_URL='http://localhost:5081'
$env:IDENTITY_MAILPIT_URL='http://127.0.0.1:8025'
$env:IDENTITY_SMOKE_REPORT='<repository>\artifacts\identity-smoke-result.json'
node scripts\smoke-identity.mjs
```

This explicitly creates one sample account and performs captured email confirmation, antiforgery login, PKCE code exchange, profile read, privilege denial, refresh rotation and logout revocation. No passwords, token values or message body are printed. Use the development service only.

## Container and production limits

Build from repository root with `docker build -f Backend/Services/Identity/SRECommerce.Identity.API/Dockerfile -t srecommerce-identity:dev .`. The image uses a non-root runtime user and a readiness healthcheck. Production needs configured TLS/certificates and a writable protected key-ring volume owned by that user. The application must be served over HTTPS directly; no untrusted forwarded headers are accepted.

Windows integrated authentication used natively does not automatically work inside Linux containers. The verified Compose profile uses `host.docker.internal,1433`, the pre-existing SQL mixed-authentication mode and the restricted Identity runtime login. No server-wide authentication/firewall setting was changed. Both containers are healthy; container readiness and 13 real-process smoke checks passed against the host SQL database. See [Docker local development](../docker-local-development.md) for the verified commands and resource limits. No volume pruning/reset is authorized.

```powershell
docker compose --profile identity-api config --quiet
docker compose --profile identity-api build identity
docker compose --profile identity-api up -d --no-build
docker compose --profile identity-api ps
```

The local native Mailpit process was stopped before Compose took the same loopback ports. Its separate ignored message database remains intact. Compose persists its own messages, development certificates and key ring in named volumes. Development key-ring files are not encrypted at rest inside that volume; protect local Docker storage. Production requires certificate-protected data-protection keys and configured signing/encryption certificates.

## Test evidence and recovery

SQL integration tests use unique SRECommerce_IdentityTests_* databases and guard the name before migrating; test data is retained rather than silently dropped. They exercise real SQL migrations/rowversion and real Identity/OpenIddict HTTP middleware. The root .NET 8 regression suite must also remain passing. Keep source database checksums and pre-existing SQL backup history. No authority/frontend cutover is part of this service phase.
