# Cart API and SQL ownership

`SRECommerce.Cart.API` contains its own solution and five projects. Controllers call `ICartService`, application logic uses `ICartRepository`/`ICartAccess`, and infrastructure owns `SRECommerce_CartDB` plus HTTP dependencies. Domain entities are ShoppingCart, CartItem, CartSession, CartOperation and CheckoutPreparation. SQL also owns audit/outbox/inbox tables; no cross-service foreign keys or SQL reads exist.

## Guest and customer routes

Guest base: `/api/v1/public/tenants/{tenant}/cart/carts`. Customer base: `/api/v1/tenants/{tenant}/cart/carts`.

| Method/path | Request | Result |
| --- | --- | --- |
| POST base | `{ id }` | Create/resume a guest cart or obtain the current customer's active cart |
| GET `/{id}` | — | Saved lines, revision, expiry and SQL rowversion |
| PUT `/{id}/items` | `{ operationId, variantId, quantity, version }` | Set an authoritative published SKU quantity |
| POST `/{id}/items/{variant}/remove` | `{ operationId, version }` | Mark the line inactive, preserving history |
| POST `/{id}/preview` | `{ id, couponCode? }` | Current Pricing quote, Inventory availability and `canPrepare` |
| POST `/{id}/prepare` | `{ id, version, couponCode? }` | Immutable, short-lived checkout preparation |
| POST customer `/{id}/merge` | `{ operationId, guestCartId, guestVersion, version }` | Merge guest quantities once and revoke the guest session |
| GET customer `/recovery` | — | Latest eligible expired cart with ID, expiry and product count, or 204 |
| POST customer `/{id}/recover` | `{ operationId, sourceCartId, version }` | Restore eligible lines into the current cart and return the saved result |
| GET customer `/{id}/reminder` | — | Read `{ available, enabled, queued }` for the account's current cart |
| PUT customer `/{id}/reminder` | `{ enabled }` | Opt in or cancel a reminder and return the saved preference |

The Cart page offers recovery after it opens the customer's current cart. The previous cart must belong to the same account and tenant, have expired within the past 30 days, and have settled checkout claims. Recovery revalidates products against the current Catalog and preserves quantities already in the destination cart. The source closes as merged and retains its history. A repeated operation ID returns the same result. Checkout still obtains current prices and stock through its usual flow.

### Saved cart reminders

An authenticated Customer or B2BBuyer can opt in on their own nonempty active cart. The scheduler waits at least 24 hours from consent and the most recent cart activity. It records one `cart.reminder.due.v1` event per cart in the same SQL transaction as the queued marker. The event carries the cart and customer IDs. Notification deduplicates the event and uses a configured storefront origin to build the sign-in link.

Before attempting email delivery, Notification checks the tenant modules, the customer's current verified email, their Notification email preference, and whether the exact queued cart is still enabled, active, nonempty, inactive, unexpired and free of a held checkout claim. Events become ineligible 24 hours after queueing. Cancellation suppresses an outstanding reminder if it reaches Cart before the last eligibility check. The email address is resolved for each attempt and is kept out of the reminder event and stored reminder job.

The feature is off by default. To enable it, first apply [the Cart migration](../database-migrations/cart-saved-reminders.sql), then configure the broker route `cart.reminder.due.v1` for Notification and authorize the Notification client for `internal_cart`. Both services need `Messaging__Enabled=true`. Notification needs delivery enabled and `CartReminders__StorefrontOrigin` set to the trusted HTTPS storefront origin. A development loopback origin such as `http://localhost:4000/` is also accepted. Once those dependencies are verified, set `CartReminders__Enabled=true` in Cart. The Cart worker and its internal eligibility endpoint read the Cart setting. The existing local review credential hold covers new broker permissions and scope grants.

Guest calls require `X-Cart-Key`: a canonical 43-character base64url encoding of 32 cryptographically random bytes, generated by the browser. Only SHA-256 of those bytes is stored in SQL. A cart GUID alone grants no access. Do not put the key in URLs, logs or Git. The same key is required on customer merge to prove ownership of the guest cart.

Customer IDs come only from live Identity authorization. Other customers' cart IDs return 404; selected-tenant/module checks remain mandatory. Bodies reject unknown fields, including client prices, tax, role, user ID or tenant ID. All responses use `Cache-Control: no-store` through shared hosting.

Each item/merge operation has a tenant/cart-scoped immutable receipt. Replays with identical payload return the saved result even with the original rowversion; changed payload under the same operation ID returns 409. Concurrent edits have one version winner. Carts hold at most 50 distinct active variants; quantity is 0.001–1000 with at most three decimal places. Source items are soft-deactivated, never physically deleted.

Guest carts expire after seven days of item activity; customer carts after thirty. Expired access returns 410. Creating a customer cart after expiry closes its previous active cart and creates a new one atomically. Guest merges close the source, add matching quantities, reject overflow and require both versions. Current Catalog visibility is checked for all destination lines.

## Price, stock and preparation

Saved cart state is independent of previews. Preview calls the owning Catalog, Inventory and Pricing APIs; it never computes a selling price or trusts browser totals. Catalog's bounded `shopping-products?ids=...` endpoint returns only current published/visible products and applies actual customer/B2B role eligibility. Inventory's protected availability endpoint applies the same live Catalog eligibility. Guest queries exclude B2B-only products and stock.

Preparation requires the current version and sufficient **tracked** stock, plus a valid server quote for exactly the cart's SKUs/quantities/customer. Its document retains public item metadata and the quote; it contains no guest capability, bearer token, cost price or card data. Idempotent preparation requests preserve their original identity. Expired preparations, changed cart revisions or changed role context require a fresh request.

Preparation does not reserve stock, claim coupon capacity, create an order or process a payment. Order owns the checkout saga and must revalidate/claim dependencies before accepting an order. The Angular readiness panel states that integration boundary explicitly.

Internal `POST /internal/v1/tenants/{tenant}/cart/preparations/{id}/verify` accepts `{ userId }`, requires a scoped Order machine token, verifies customer identity (or the guest capability), expiry and unchanged active cart revision. A human token cannot invoke it. These routes are blocked at YARP. Machine proof is trusted only from the explicitly permitted Order identity; the future Order public endpoint must establish that user's current authority independently.
